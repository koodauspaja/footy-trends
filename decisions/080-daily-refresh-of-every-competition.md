# 080 — Daily refresh of every competition: decisions

Feature #828, spec `specs/080-daily-refresh-of-every-competition.md`. Arvauspeli, the predictions log and the settling of guesses read stored rows and never open a competition page, so a fixture the provider added or moved reached them only when someone happened to open that page (#815). Once a day, every competition's current season is now fetched and stored.

| Decision | Why |
|---|---|
| **A step of the hourly `predictions -- log` run, in the run that starts in the 03 hour UTC**, before that run reads its candidates | Miikka chose 03:00 UTC. Inside the hourly run, the step shares its pacers (`providerPacers` in `src/lib/providers/pacer.ts`, which both now take), so the step and the near-kickoff refresh never together exceed football-data's 10 a minute. A second cron service would pace only itself, on the same key. Running first means that same run's refresh, settling and predictions already see what it stored |
| **`isDailyRefreshHour` reads the run's start, `getUTCHours() === 3`** | The run starts on the hour, so the check needs no state. A run that never starts, or crashes before the step, means no refresh that day; nothing catches up on its own (spec, Edge Cases) |
| **`npm run predictions -- refresh` runs the step alone**, with the same summary lines and exit code | Staging has no cron, and a failed 03:00 run otherwise waits a day |
| **The step calls the providers itself, each request through the pacer, and writes with the functions everyone uses**: `getSeasonMatches` and `synchronizeMatches` of each provider, TASO's `getSeasonGroups`, and `storeSeasonGroups` | The spec first said the step would go through the pages' own refresh functions. Those call the providers unpaced, so going through them would put the step's requests beside the hourly run's paced ones. The provider functions are the same the pages call, so the 15-minute response cache still answers a season fetched in the last 15 minutes. The spec was corrected to this before the pull request |
| **`storeSeasonGroups` is cut out of `getSyncedGroupTeams`**, which now calls it | The group write (normalise, carry starting points, sync) had one home, inside the page's refresh. The step needs the write without the page's fetch, and one copy of it keeps the two from drifting |
| **TASO's current season is `resolveTasoSeasonCeiling`'s**, the newest season TASO lists | It is what the season selector tops out at, and it covers a season TASO has published but not started. A season with no matches yet is fetched, stores nothing, and is not a failure |
| **While that season has no matches, the season the page shows is refreshed too** (`seasonShownBeforeMatches`, cut out of `resolveTasoSeasonContext`, which now calls it) | The spec first said the season before an empty one is past and not fetched, and this record first said a page does not refresh it either. Both were wrong: TASO's discovery is one answer for every competition, and a domestic page treats the season it lands on, the newest with matches, as active (`domestic-page-context.ts`), so a visit does refresh it. Review on the pull request found the gap: once TASO lists next season anywhere, the step would have stopped refreshing a season still being played (a playoff, a moved cup final). Miikka chose to fetch the shown season, so the step does what a page visit does. One rule, used by both, keeps them from drifting |
| **A season with no matches gets no group fetch or write** | `storedTasoSeasons` counts group rows, so group rows for an unstarted season would make it the newest stored one, and every domestic page would land on it, empty. Pages never wrote groups for such a season; the first version of the step could. Sourcery found it on the pull request |
| **The shown season is refreshed unless the newest one refreshed with matches**, a failed newest one included | A failure says nothing about whether the newest season has started, and the shown one may still be the season being played (Sourcery, on the pull request) |
| **A failed discovery is named but still refreshes the season it fell back to**, unless nothing is stored | The ceiling falls back to the newest stored season, as a page's does, and that season may still be the current one. With nothing stored, the fallback is the competition's first season, which is past, so nothing is fetched (review on the pull request) |
| **football-data's seasons are the active one and, when the competition response lists one, the upcoming one**: `upcomingSeasonId` is added to `getSeasonContext` | Miikka chose to include the upcoming season, so a published fixture list is stored before its opening day. `getSeasonContext` already computed it for the selector |
| **The foreign competitions are `SUPPORTED_COMPETITIONS` whose region is `foreign`** | That is the ten the issue names, and the ten that are predicted. The World Cup and the Euro are `national-teams`, read only by their own pages, and Miikka left the national-team pages out |
| **Every domestic competition gets its group tables, the cups included** | Every domestic page reads them through `classifySeasonGroups`, the knockout cups' match lists included |
| **A manual `refresh` is run away from the top of the hour** (`docs/infrastructure.md`) | Run by hand it is a second process on the football-data key, which the pacers cannot see; the first measured run below got 429s for that reason |
| **No new guard against concurrent writers, a partial write or derived caches** | Three of Sourcery's findings on the pull request. A page and the hourly run already write the same seasons with the same syncs, and their overlap is the one `decisions/678-stale-snapshot-written-last.md` accepts. Matches written before the group write fails are the provider's current ones, as a page stores the two independently. Only a forced refresh moves a season's cache generation (`decisions/691-computed-cache-generations.md`); a page's and the hourly run's syncs do not, and forecasts expire in 15 minutes |
| **One `error` line per failure, `Daily refresh of a competition failed`**, with `source`, `code` and `seasonId` | The pages' refresh functions log their own warnings, but the step does not go through them. The spec's Logging section was corrected to this line |
| **A competition's matches and groups are one unit**: if the matches fail, the groups are not fetched, and either failing names the competition-season once | The count is of competition-seasons refreshed, and a half-refreshed one is not refreshed |
| **The run's report gains `daily`**: the count, or null in the hours the step does not run | The printed summary puts `Daily …` first in that hour, and the run's failures list the step's first |

## Measured

On 2026-11-23, `npm run predictions -- refresh` against the real providers, into a scratch database (created, migrated and dropped after each):

| Run | Result |
|---|---|
| 20:02 UTC, first version, while production's hourly cron was still using the shared football-data key | `Daily 22 competition-season(s) refreshed`, exit 1. football-data answered 429 for `PD`'s competition and `PPL`'s matches; both were named (`daily football-data PD season`, `daily football-data PPL 2026`) and the other 22 stored |
| 20:22 UTC, first version, nothing else on the key | `Daily 24 competition-season(s) refreshed`, no failure, no 429. Every domestic competition fetched only its empty 2027; no 2026 row was stored, which is the gap review then found |
| 21:38 UTC, with the shown season | `Daily 38 competition-season(s) refreshed`, exit 0, 128 s: 70 TASO calls (the spec's most) and 20 football-data calls. Each domestic competition's empty 2027 and its shown 2026 were fetched: 1 891 domestic 2026 matches and 1 270 group rows across all 14, and 3 440 matches across the 10 foreign competitions. No upcoming football-data season was listed |

TASO lists 2027 (`spljp27`, `Liigacup27`, `M1LCUP27`) as every domestic competition's newest season, with no matches yet. The second run's football-data calls stopped twice for minutes, which `pmset -g log` shows were the machine sleeping, not the step; the third ran under `caffeinate`.

After the group change, a fourth run at 22:17 UTC stored the same: 38 competition-seasons, every domestic 2026 season with its groups, and no 2027 group row. Its responses came from the cache an earlier check had filled, so it made no provider request; the four calls per competition are counted in `tests/unit/lib/predictions/daily-refresh.test.ts`.
