# 880 — Provider requests bounded while a provider fails: decisions

Bug #880. A page view's provider requests were bounded only while the provider answered: the response cache stores a success for 15 minutes, but a failure was not stored, so every page view asked again (and once more after a 429), and requests that missed the same key at the same moment each made their own. A visitor repeating page loads during an outage could spend the football-data key's 10 a minute, which production, staging and the hourly run share, or keep hitting TASO. Found while designing #878, which was changed to read stored rows only for that reason.

| Decision | Why |
|---|---|
| **A path whose request finally failed is left alone for 60 seconds** (`FAILURE_COOLDOWN_SECONDS`): a request for it meanwhile throws `ProviderCoolingDownError` without asking the provider | Miikka chose 60 seconds. "Finally" is a network error, a timeout, or a non-2xx after the one 429 retry; a 429 its retry clears starts nothing. Every caller already treats a failed request as a failed refresh and serves the stored rows, so a reader sees what a failure shows today, and the provider is asked at most once a minute per path however many page loads arrive |
| **In `fetchProviderJson`, for TASO and football-data alike** | Every request of both providers goes through it, so one place bounds them all. TASO publishes no limit, but has refused busy addresses before |
| **Kept in Redis, keyed by provider and path, `provider-cooldown:<provider>:<path>`**, TASO's trailing `hash` left out | Shared by every process, so page views and the hourly run see one cooldown. A TASO path is signed on every request; without stripping the signature, the same path signed again would be a different key |
| **A request the caller's own signal gave up on starts no cooldown**; a request whose attempt timed out does | The provider did not fail when a caller stopped waiting, such as the health check at its own deadline. The per-attempt timeout (`decisions/363-render-timeouts.md`) is the provider being too slow, the same for every caller, so it counts. Found by the code review before the first push |
| **If Redis cannot be read or written, the request goes ahead** and the failure is logged as any cache failure | As before the cooldown existed: Redis being down must not stop the app from asking its providers |
| **A skipped request is not logged** | The failure that started the cooldown is logged, and the caller logs its own failed refresh; a line per skipped request would let a visitor flood the logs instead of the provider |
| **Misses of the same key at once share one fetch** (`sharedFetch` in `getCachedUnlessDegraded`), in-process, and a failure is shared and forgotten too | The web service runs one instance, so one process covers every page view. It applies to every cached read, the computed Elo, Poisson and quality figures included, which gain the same: one computation per key at a time |
| **Sharing a fetch shares its failure**, a render timeout included | No cached fetch carries a caller's own signal: only `getCurrentSeason`, the health check's, takes one, and it is not cached. The render deadline is the per-attempt timeout, the same for every caller, so a timeout one caller met is the one the others would meet. The code review asked; this is why it stays |
| **The token-gated health check respects the cooldown** | During one it reports the provider as failing without asking it, which is the state it would find |
| **`tests/unit/lib/taso/taso.test.ts` and `football-data.test.ts` mock Redis**, holding no cooldown | The unit setup removes `REDIS_URL`, so the client falls back to `localhost:6379`: a developer's own Redis, and nothing in CI. Without the mock, CI's unit run failed 32 of their tests (measured with the local Redis stopped), and a local run wrote cooldowns into the developer's Redis. The cooldown is tested with the request itself, against a map |
| **`taso.test.ts`'s stubbed `fetch` rejects a signal already aborted** | As real `fetch` does. The cooldown's Redis read now comes before `fetch`, so a caller aborting at once hands `fetch` an aborted signal; the stub only listened for a later abort and waited forever |
