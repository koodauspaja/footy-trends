# 841 — Commit subjects say what changed: decisions

Chore #841. Two commits on #840 and one on #807's branch were titled "answer Sourcery's first/second review". A subject like that names the review and says nothing about the change. The rule was a note, and the note did not hold. Now a git `commit-msg` hook refuses such a subject, and CI's `Commit messages` job, a required check, refuses a pull request that carries one.

| Decision | Why |
|---|---|
| **What is refused:** seven phrase shapes, each naming the review itself. They are "answer/address/respond to/reply to" with the review within three words, the same verbs with the reviewer right after (`Sourcery`, `Sonar`, "the reviewer"), "fix review/Sourcery's/Sonar findings", "fix findings from … review", "apply … suggestions" with nothing but review words between, "review round" (not "review round-trip") and "per … review". A phrase is read within one clause: the subject is cut at `,` `;` `:` `—` and at "and", "or", "but" | A shape needs both the act and the review in it. So `chore: check:sourcery says which kind of Sourcery review a head has` and `fix: a table TASO serves as unplayed is answered with our own` pass: they name a change that is about reviews or answers. Cutting at clauses keeps `answers come from the cache, and the comments table is dropped` a change, for every shape at once rather than in each expression. Each expression is a literal with an inflection as `\w*`, so Sonar measures it and it stays under its complexity limit |
| **Tested against every subject on `main`** (611 when written, kept in `tests/unit/scripts/hooks/main-subjects.txt`): all pass except six from before squash merges, which must fail | `main` is the record of what the project accepts as a subject, so a rule that refused one of those would be wrong. The six (`refactor: address Sourcery review on PR #120` and five like it) are the same mistake, so the test proves the rule catches the real thing |
| **Where it runs:** the `commit-msg` hook on the subject being committed, and the CI job on every commit `base..head` adds and on the pull request's title. The job is limited to the actors the other jobs are, like every job that runs pull-request code | The hook stops it as the commit is made, for anyone with the hooks installed. The job covers `--no-verify` and commits made elsewhere, and as a required check it blocks the merge. The title matters because a squash merge makes it the subject that lands on `main`. It is checked when the pull request opens or is pushed to, as a title, not a git message, so a leading `#` is part of it. A title edited later is not rechecked until the next push: the squash dialog lets whoever merges rewrite the subject at that moment anyway, so no check before the merge can promise the subject that lands, and rerunning every CI job on each edit of the description would cost more than it catches |
| **Only the subject is read** | The subject is what `git log --oneline` and a review list show. A body may explain which review a fix answered |
| **Not a `verify` stage:** `check:commits` is in `NOT_A_STAGE` | The hook has already checked each commit as it was made, so a local stage would repeat it |
| **A range git cannot read fails the job** | An unread range is not a pass, the same as `check:boxes` (decisions/463) |

- **The required check is set before the merge**, and was, on 2026-11-21. The docs list it as required, so it is true when they land. Until the job is on `main`, a pull request without it waits, as it would for being behind `main`.

Not done:

- A full message format (commitlint, conventional types).
- Rewriting the subjects already on #840's and #807's branches, which the squash merges replaced.
- Running the checker from the base revision so a pull request cannot change it. Under `pull_request` the workflow file itself comes from the pull request, so a pull request that wanted to could drop the job as easily as change the checker. What covers it is the diff, read before the merge, as for every job here.
- Running the job for actors outside the allowlist. Every CI job skips for them, and a skipped required check counts as passed (`docs/infrastructure.md`, Rulesets). This job is no weaker than the unit tests there, and only the owner and the collaborator can merge.
- A non-default `core.commentChar`, which nobody here sets.
- Every wording a subject could use. The shapes are the ones this repository's history has shown, and the test reads all 611 subjects on `main` so a new shape cannot refuse a real change unseen; guessing more wordings ("incorporate", "implement") trades that for coverage nobody has needed. People are not listed as reviewers, so the rule does not go stale when a collaborator changes.
- A commit subject starting with `#`. Git drops such a line as a comment before committing, so the hook reads the message as git will, and CI reads each subject from `git log`, where nothing is skipped.
