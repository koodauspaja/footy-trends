# 078 — Arvauspeli: private groups: decisions

Feature #764, `specs/078-private-groups.md`. Players form private groups,
joined by an invite link, each with a leaderboard of its members' season
balances beside the public one.

| Decision | Why |
|---|---|
| The rules are a module of their own, `guessing-game-group.ts`: the limits (10 groups per player, 50 members per group), the name's check, the invite token, the shape of an id or a token from the browser, and who owns a group | S1, S7. Pure, so every boundary is tested without a database |
| A group's name is checked as specs/077's nickname is, by its own functions: normalised the same, 3–30 code points, `hasAllowedCharacters` (exported from `nickname.ts` for this) and the same word lists. Not unique | S7 |
| Two tables, migration `0029_create_game_group`: `game_group` (name, `invite_token` unique, created at) and `game_group_member` (group, player, joined at), unique on the pair, cascading on the group's deletion and on the player's `game_player` row, as every game table does | The spec's API & Data |
| **The owner is not stored.** It is the membership with the lowest id, the member who joined earliest (`ownerOf`). Leaving, or an account's deletion, passes ownership on with no write of its own | S3. A stored owner would need moving on each of three paths, two of them cascades the app never sees |
| **A trigger deletes a group once its last membership is gone**, `game_group_member_last_out`, in `0029`. It locks the group's row first, so two last members leaving at once are decided one after the other and the second sees the group empty | S3: the last member leaving deletes the group. Membership rows also go by cascade when an account is deleted, by the user or by the admin, which no group code runs on; one rule in the database covers all of them. `drizzle-kit` does not track triggers, so it was added by hand to the generated migration before that ran anywhere, and `docs/infrastructure.md` names it |
| Every write locks before it checks: a create or a join locks the player's `game_player` row (`no key update`), then a join the group's row (`for update`); leaving and the owner's actions lock the group's row. So two joins cannot pass 50 together, nor one player's joins 10 | The spec's API & Data |
| A refusal is thrown inside the transaction, so joining by the link, which joins the game first for a reader not yet playing, writes both or neither: a full group leaves the reader as they were | S6: `Liity peliin ja ryhmään` joins both in one press |
| A join locks the group in the same statement that finds it by its token, so a join that waited on a renewal or a deletion reads the row again once it holds the lock, and finds the link names no group | The spec's API & Data. Found in self-review: looked up first and locked after, a join could pass through a link renewed in between |
| `joinGame`'s body is `joinGameIn`, taking the caller's transaction | The join above. `joinGame` calls it in a transaction of its own, as before |
| The leaderboard's read is split: `readBoardEntries` reads every player of a season once, and `rankBoard` ranks them, for everyone or for a group's members. `readBoard` is the two together | S4: a group's board is the same balances, members only, by specs/073's listing rule and ties |
| The owner removes a member by the membership's id, not the user's | The page never needs another user's account id |
| The group page lists every member under `Jäsenet`, the owner and the reader named, and the owner's `Poista ryhmästä` is on those rows. The spec put it on each member's board row, but the board lists only members with a guess this season | S3. The owner must be able to remove a member who has not guessed. The privacy line already says members see each other's nicknames |
| A signed-out reader on a group's page is asked to sign in, as on `/arvauspeli`, rather than given the 404 | The prompt is the same for any id, so it reveals nothing, and a member following their own bookmark gets in |
| The invite page shows a signed-out reader the group's name, as the spec's string has it; a link that names no group shows no name, signed in or not. A token not shaped as `newInviteToken`'s is answered as a link that names no group, without a read | The spec's UX, and S2 |
| The invite link is shown in full by the address the reader is on, read in the browser (`useSyncExternalStore`); the server renders the path alone | The app has no setting for its public address outside sign-in |
| A group's and an invite's paths are built by `guessing-game-group-paths.ts`, which the server's pages and the browser's controls both import | A value exported from a `"use client"` module reaches a server component as a reference, not a value: the `Ryhmät` list linked to the reference's text until the end-to-end test clicked it |
| Creating a group opens its page; joining opens it too; leaving or deleting returns to `/arvauspeli`. A refusal because the page no longer matches the group (`not-member`, `not-owner`) reloads the page, which a removed member sees as the 404 | The spec's Edge Cases: a group deleted while a member has its page open |
| Logging: one `info` line per write, `Arvauspeli group created`, `joined`, `left` (with whether it emptied the group), `member removed`, `renamed`, `link renewed`, `deleted`, and `ownership passed` when the owner leaves. A refusal is `Arvauspeli group refused` with its reason, `self` and `not-player` among them. An account's deletion passes ownership with no line of its own | The spec's Logging. The spec named `ownership passed` on account deletion too; the cascade runs in the database, and the deletion's own line already records it. The spec now says so |
| Tests: unit for the rules, the store over a faked client, the actions, the controls, the section, the pages; integration against Postgres for the board, the limits under a race, the owner passing on and the trigger; end to end in `guessing-game-group.spec.ts` | Spec, Tests Required |
