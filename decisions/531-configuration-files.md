# 531 — Configuration files: what their comments said

The comment rule's batch for `scripts/` and the configuration files moved the
long comments of the files below here, each as it was written, under the line
it sat above. A file's first line cites this record. Cut at `5b180e0`.

## `sonar-project.properties`

### Above `sonar.sources=.`

Everything, not just `src`. The organization has stock profiles active for
GitHub Actions (34 rules), Secrets (356), YAML, JSON, Docker and HTML, and
with `sonar.sources=src` none of them ever saw a file: 534 lines of workflows,
11 scripts, 10 SQL migrations, docker-compose.yml, railway.toml (since
replaced by .railway/railway.ts), .env.example
and 87 Markdown files were invisible.

The Secrets rules are the point. REVIEW_RULES.md says never commit an API key,
and until now nothing enforced it — a key pasted into a workflow, a doc or
.env.example passed every check we run. See #258.

### Above `sonar.sourceEncoding=UTF-8`

Stated rather than inherited from whatever charset the runner defaults to. The
repository is UTF-8 throughout: no BOMs, and every tracked text file decodes
cleanly.

This is *not* what "problems with file encoding in the source code" was about —
that was binary files being read as text, and is fixed by the exclusions below.

### Above `# Without this, the scanner uploads analysis and exits successfully as`

There is no `sonar.typescript.tsconfigPath`. The documented property is
`tsconfigPaths`, plural, and #258 removed the singular line rather than
correcting it: with no property set the analyzer traverses from the project
root and finds the one tsconfig.json by itself. A line that either does
nothing or restates the default is the kind that looks load-bearing later.

### Above `sonar.qualitygate.wait=true`

Without this, the scanner uploads analysis and exits successfully as soon
as the scan itself completes — the Quality Gate is evaluated afterward,
asynchronously, on SonarCloud's servers, and its pass/fail never reaches
the CI job. This makes the scanner poll for the gate result and fail the
job (and therefore the "SonarCloud scan" GitHub check) when it does.

### Above `sonar.exclusions=**/*.ico,**/*.png,**/*.jpg,**/*.jpeg,**/*.webp,**/*.g`

Build output, dependencies, generated reports and the migration snapshots
Drizzle writes. Nothing here is authored, so an issue in it is noise.

`tests/**` is here because `sonar.sources=.` contains it and `sonar.tests`
claims it, and a file indexed as both source and test fails the analysis
outright. This property applies to main sources only, so the tests are still
indexed as tests — with the test-specific rules, and out of coverage and
duplication where they belong.

`package-lock.json` is 800k of generated JSON that the JSON sensor would
otherwise parse on every run.
Binary files are excluded by extension, not by directory. `sonar.sources=.`
indexes everything, so a favicon and the avatar image fixtures were read as
UTF-8 text and reported one "Invalid character encountered ... at line 1" each.
They carry no analysable source, so the fix is to stop indexing them rather
than to describe their encoding.

### Above `sonar.test.exclusions=**/*.ico,**/*.png,**/*.jpg,**/*.jpeg,**/*.webp,*`

Both files are static data tables whose repeated shape is necessary,
readable data rather than copy-pasted logic. Excluded from duplication
analysis rather than contorted into something templated just to dodge the
metric.

src/lib/competitions.ts — 9 competitions, each a {code, name, flagUrl,
country} object literal.

src/lib/domestic-competitions.ts — 10 competitions, each with its list of
{fromSeason, categoryId} eras. The three junior competitions share a shape
because they share a history: all three were renamed in 2026 and again in
2017, so their entries differ only in the ids. Factoring that into a helper
would hide the season boundaries behind positional arguments and still not
fit T18 SM, which has two eras rather than three.

The four workflows repeat job scaffolding — `runs-on`, the actor guard, the
Node setup — because that is what workflows look like. Indexing them without
this would push `new_duplicated_lines_density` over the gate's 3% the first
time one is edited, which is the metric that already blocked a pull request
this week. The migration SQL is generated by drizzle-kit and repeats for the
same reason — it is not written by hand and cannot be refactored.
The `.sql` files here are generated **PostgreSQL** DDL from drizzle-kit, and
`sonar.plsql.file.suffixes` defaults to `sql,pks,pkb` — so the **Oracle**
PL/SQL analyzer claimed them and then asked, on every run, for a Data
Dictionary this project will never have (#296).

Dropping `sql` from the list leaves the Oracle-only suffixes. Nothing here is
PL/SQL, so nothing stops being analysed by a rule that could apply; the
migrations stay indexed for the Secrets rules, which is why #258 widened the
scan to the whole repository in the first place.
The same list again for the test side. `sonar.exclusions` governs *sources*
only, and `sonar.tests=tests` re-indexes everything under it — which is why
`tests/**` being excluded above did not stop the avatar fixtures warning.

The groups below, and how many entries each holds. Machine-readable because a
count in prose is the thing that drifts — #389 got the same count wrong twice,
and review on #411 read these ones as wrong when they were right, which is the
same problem from the other side. `tests/unit/scripts/coverage-exclusions.test.ts`
fails if any line here disagrees with the list itself.

  exclusion-count: total 26
  exclusion-count: connects-at-import 2
  exclusion-count: tested-runner-half 16
  exclusion-count: tooling-configuration 8

**26 entries.** #403 took the list from 31 to 26, `predictions.ts` made it
27 (specs/052), and `src/db/index.ts` leaving made it 26 again (#536). Five
files were excluded because nobody
had asked how they would be tested rather than because they could not be:

- `src/instrumentation.ts` — a test had existed since #174. The exclusion was
  simply stale, which is how a real gap hides (#258 removed two of those).
- `src/app/global-error.tsx` — a React component, and Testing Library was
  already set up. It is the boundary Next renders when the app itself has
  failed, and nothing asserted it rendered anything at all.
- `src/instrumentation-client.ts` — runs `Sentry.init` at import, which a test
  can assert *is* the thing worth pinning: which variables are read, and that
  `integrations` is deliberately absent rather than empty.
- `scripts/e2e-freshness-git.ts` and `scripts/e2e-freshness-reporter.ts` — the
  spawn and the filesystem call are injected now, the way `docker.ts` injects
  its spawn. Which flags git is given (`-z`, paths after `--`) is the whole
  correctness argument for the fingerprint the pre-push hook rests on, and it
  is assertable only this way.

What is left falls into three groups, each with a reason that survives the
question "why not inject that?".

**They open a connection at import.** `src/lib/redis.ts` constructs its
client at module load, and `src/db/migrate.ts` migrates. A test that imported
one would connect. `src/db/index.ts` was a third until #536 made its client on
first use; it is measured now.

**The runners' decisions live in a tested half.** That is the
`*-plan.ts` split working as intended: `backfill.ts` and `backfill-run.ts`
beside `backfill-plan.ts`, `grant-admin*.ts` beside `grant-admin-plan.ts`,
`e2e-freshness.ts` beside `e2e-freshness-plan.ts`, `coverage-gaps.ts` beside
`coverage-gaps-plan.ts`, `generate-migration.ts` beside `migration-name.ts`,
`release-version.ts` beside `next-version.ts`, `release-pr.ts` beside
`release-pr-plan.ts`, `verify-sentry.ts` beside `verify-sentry-plan.ts`,
`review-findings.ts` beside `review-findings-plan.ts`, `with-test-db.ts`
beside `with-test-db-plan.ts` (added in #403), and `ensure-services.ts`,
`db-reset.ts` and `services-run.ts` beside `services-plan.ts` and
`preflight.ts`, and `predictions.ts` beside `predictions-plan.ts` (specs/052). Only the IO shell is excluded, and each runs `main()` at
import or opens a connection: importing `db-reset.ts` would reset the
importer's database, and `with-test-db.ts` would create and migrate one.

`scripts/migration-name.ts` is deliberately **not** here. It is that runner's
pure half — the naming rule and the argument parsing — and it is unit tested
at 100%. It is only the name that differs: it is shared with
`tests/unit/db/migrations.test.ts` rather than belonging to one tool.

**The rest are the tooling's own configuration** — Next, Drizzle, Playwright,
PostCSS, Sentry and Vitest. Widening `sonar.sources` indexes them as source,
and none appears in `coverage/lcov.info`, so the Zero Coverage Sensor would
score each 0% and drop the project below the 100% this repository holds itself
to. They configure the tools that run the tests; there is nothing in them a
unit test could assert that would not simply restate the file.

**The entry points added since #400 are not here at all.**
`scripts/setup-main.ts` and `scripts/verify.ts` hand the decision to
`entry-point.ts`, which compares `process.argv[1]`, so a test imports them and
nothing runs. The same shape would retire two or three of the runners above;
each needs its own check that importing it really does nothing.

## `.github/workflows/release.yml`

### Above `name: Release`

Runs the full suite against the release branch, which is what production
deploys from. Separate from ci.yml deliberately: this is the only place e2e
runs (see #81), and static analysis is *not* repeated here because a release
PR carries commits already reviewed on their way into main.

The `push` trigger is not optional. Railway only offers its "Wait for CI"
setting when a workflow has a push trigger for the tracked branch, and that
setting is what stops a deploy whose tests failed. `pull_request` alone would
gate the merge but leave the deploy ungated.

`workflow_dispatch` exists so this can be exercised without cutting a
release — the first real release should not be the first time it runs.

Deliberately *without* ci.yml's `github.actor` guard. GitHub counts a skipped
required check as satisfied, so a guard that skips would let a release PR
merge with no tests run at all — the one hole this gate cannot have. A fork
pull request receives no secrets, so the e2e job fails rather than leaking
them, and failing is the correct outcome for an untrusted release PR.

### Above `concurrency:`

Concurrency here protects the *gate*, not the provider — those turn out to be
incompatible goals with this mechanism, and the gate wins.

GitHub keeps one running and one pending run per group, and a newly queued run
evicts the pending one even with `cancel-in-progress: false`. So any group two
runs can share is a group in which a push run's status can be silently
dropped, and that status is what Railway's Wait for CI is waiting on. Push
runs therefore get a group per commit: never queued behind anything, never
evicted, never cancelled.

That means overlapping live-provider load is possible, and this workflow does
not pretend otherwise. If football-data.org's rate limit starts producing
false failures, the fix is a CI-only provider key rather than a shared
concurrency group — a rate-limited run fails safe by blocking a deploy, while
an evicted push run removes the gate entirely.

Pull-request runs supersede their own predecessors, which is only ever useful.

### Above `run: npm ci --ignore-scripts`

`--ignore-scripts` blocks dependency lifecycle scripts, which are how a
compromised package runs code on a runner holding our tokens
(githubactions:S6505). Nothing here needs them: the only script in
package.json is husky, which installs git hooks no CI job uses, and
the two dependencies that fetch binaries — esbuild and @sentry/cli —
resolve them from optional platform packages instead. Verified in #258
by installing this way and running typecheck, lint, the full unit
suite and a production build.

### Above `BETTER_AUTH_SECRET: ci-not-a-real-secret-ci-not-a-real-secret`

Dummy literals, not secrets. No test completes a real Google sign-in —
Google blocks automated browsers — so nothing here needs a real
credential. They exist because src/lib/auth.ts fails fast on a missing
variable rather than at first sign-in. See specs/023-google-oauth-login.md.

### Above `- name: Install Chromium for Playwright`

Chromium only, per #81. `--with-deps` because the runner has none of

An npm script rather than `npx`, which is allowed to fetch a package
on demand and run its lifecycle scripts (githubactions:S6505, S8543).
This runs the playwright already installed above, so the browser

### Above `tag:`

Only after every gate is green, and only on the merge itself — never on a
pull request. A tag is effectively permanent and public, so it must not be
possible to create one for a release that was rejected or that failed its
tests.

### Above `FIRST_RELEASE_VERSION: ${{ vars.FIRST_RELEASE_VERSION }}`

Names the first release. Set it as a repository variable before that
release; there is no need to unset it afterwards, because two things
keep it from touching a later one:

  - once a release is tagged, the next promotion finds that tag and
    derives from it, so the override is never consulted
  - a rerun takes the version off the tag already on HEAD, before
    the override is read at all

Not "inert once any tag exists", which is what this said before and
is stronger than the code gives: a repository whose *only* tags were
pre-release or malformed would have no previous tag either. That is
a named limitation on `firstReleaseVersion` in scripts/next-version.ts
rather than an oversight — guarding it needs a second definition of
"has this been tagged", and having two produced six rounds of
contradictions before they were reduced back to one.

### Above `tagged="$(git rev-list -n 1 "refs/tags/$version")"`

An existing tag is only acceptable if it names *this* commit —
a rerun. Pointing anywhere else means the version was already
used for something else, and publishing notes against it would
break the one guarantee the tag carries: that it identifies the
commit the tests ran on.

### Above `run: npm ci --ignore-scripts`

### Above `- name: Unit tests, shuffled`

Runs the same suite in a random order, which is the only way to catch a
test that passes because its neighbour ran first. It was not worth
running here until #384: the suite failed at random, so a red shuffle
proved nothing and would have trained everyone to re-run it. Order is no
longer a source of failure, so a failure here is a real finding.

No coverage and no gap check: those belong to the run above, and asking
for them twice would double the slowest part of this job for nothing.

### Above `BETTER_AUTH_SECRET: ci-not-a-real-secret-ci-not-a-real-secret`

Dummy literals, not secrets. No test completes a real Google sign-in —
Google blocks automated browsers — so nothing here needs a real
credential. They exist because src/lib/auth.ts fails fast on a missing
variable rather than at first sign-in. See specs/023-google-oauth-login.md.

### Above `boxes:`

The rule CLAUDE.md states and nothing enforced: a box on this pull
request's issue is ticked, or says why it is not (#463). It was skipped on
#158 and on #425 — both merged and closed with every box empty — because
nothing failed when it was.

Runs on a pull request only. On a push to `main` there is no pull request
to read, and the boxes have already been through this job on the way in.

`pull-requests: read` rather than the default: the job reads the pull
request's body and the bodies of the issues it closes, and writes nothing.

**The actor condition stays**, and #468 argued it both ways before settling.
Dropping it means a fork's pull request runs `npm ci` and this repository's
own npm script *from the fork's checkout*, with `GITHUB_TOKEN` in the
environment — a pull request can rewrite `package.json` or the script it
runs. `--ignore-scripts` narrows that; it does not close it.

What the condition costs is real and worth naming: an outside contributor
writing `Closes #N` gets no checkbox check. That is a pull request no one
can merge without a maintainer reading it, and this job enforces a workflow
only the maintainers follow — so the gap is one a human is already standing
in. Running untrusted code against a credential to close it would be the
worse trade.

Checking out the base commit instead would fix the trust problem, but then
a pull request could never change the check itself: this one adds it, and
`main` has no `check:boxes` script to run.

## `.github/workflows/taso-key-check.yml`

### Above `name: TASO key check`

The TASO key is scraped from Palloliitto's public frontend, not issued to us
(docs/setup/020-taso-api-key.md). It can stop working without notice, and
nothing else would notice quickly: pages backed by stored rows keep serving,
so the site looks fine while the current season quietly stops updating.

This asks production, once a day, whether its configured key still reaches
TASO. It needs **no secrets**: `/api/health?providers=1` is public and makes a
real TASO request with production's own key, so the check exercises the thing
that can break rather than a copy of it. A key in Actions secrets would be a
second copy that could pass while production's fails.

Failure surfaces as a red scheduled workflow, which GitHub emails to watchers
— the same signal as a failed CI run, and no new infrastructure to maintain.

## `.env.example`

### Above `DATABASE_URL=`

Database — Railway injects DATABASE_URL automatically in production.

Locally this is written by `npm run setup`, together with the password below:
postgresql://postgres:<password>@localhost:5432/footy-trends, where every part
but the password comes from docker-compose.yml. Setting it by hand works too —
see INSTALL.md.

### Above `FOOTY_POSTGRES_PASSWORD=`

The local Postgres container's password, read by docker-compose.yml. Any value
works **as long as DATABASE_URL above carries the same one** — they are two
halves of the same credential, and a mismatch shows up only as a connection
error. `npm run setup` writes one generated value into both halves at once, so
the matching is only yours to do when editing this file by hand.

Blank here on purpose: this file is tracked, and a password in it would be a
credential in git history (#292). The container is local and its port is not
exposed beyond this machine.

Named `FOOTY_` because Compose gives a shell export precedence over this file:
a generic POSTGRES_PASSWORD exported for another project would silently win
and initialise the database with the wrong value.

### Above `GOOGLE_CLIENT_ID=`

Google OAuth (added in 014, wired up in specs/023-google-oauth-login.md)
BETTER_AUTH_* replace the NEXTAUTH_* pair 014 originally described: the app
uses better-auth, not NextAuth. The registered Google redirect URI
(/api/auth/callback/google) is the same for both, so nothing changes in the
Google Cloud console. `npm run setup` generates BETTER_AUTH_SECRET and fills in
BETTER_AUTH_URL; by hand, `openssl rand -base64 32` is the secret. The Google
pair is yours to add — sign-in is the only thing that needs it, and every page
works signed out without it.

### Above `AUTH_CLIENT_IP_HEADERS=`

Which header carries the visitor's address, so rate limiting counts per client
rather than putting everyone in one bucket (#309). Left blank the app uses
`x-real-ip` — measured on staging as the one header Railway's edge overwrites,
so a client cannot set it. Only ever list a header that has been measured that
way: one the platform passes through gives an attacker a fresh bucket per
forged value, which is worse than everyone sharing one. Locally there is no
proxy and better-auth falls back to 127.0.0.1, so nothing needs setting here.

Both are comma-separated. AUTH_TRUSTED_PROXIES applies only to
`x-forwarded-for`, which is not in the default list — so reading the client
from the forwarded chain means setting BOTH, the first to `x-forwarded-for`
and the second to the edge's address or CIDR range. Check what arrives with
`/api/health?forwarded=1`.

### Above `AUTH_ALLOWED_EMAILS=`

Who may sign in, comma-separated (#314). Left blank there is no restriction,
which is what production and local development want — production's consent
screen is published on purpose. Staging sets it, because Google's Testing mode
test-user list turned out to gate nothing for an app requesting only
openid/email/profile. Adding a person is a change to this value and nothing
else — no code change and no pull request. Railway restarts the service when a
variable changes, so expect a brief redeploy; it is not a new build from source.

### Above `SENTRY_TRACES_SAMPLE_RATE=`

Production overrides — see docs/setup/021-production-environment.md.
Unset — or left blank, as below — means the development defaults (100% tracing,
PII on), which is what the Sentry wizard ships and what production must not
inherit. Blank is treated as unset deliberately: `Number("")` is 0, so an empty
sample rate would otherwise switch tracing off entirely while looking set.
The NEXT_PUBLIC_ pair is separate because browser values are inlined at build
time; a server-only variable reads as undefined there.

## `docker-compose.yml`

### Above `POSTGRES_PASSWORD: ${FOOTY_POSTGRES_PASSWORD:?set FOOTY_POSTGRES_PASSW`

From the environment, not written here. A password in a tracked file is
a credential in git history whatever it protects, and Sonar counts it as
one (#292). Compose reads `.env` from the repository root, so
`FOOTY_POSTGRES_PASSWORD=postgres` there restores the old behaviour;
`:?` makes an unset value a clear error rather than a container that
starts with no password at all.

The name is project-scoped on purpose. Compose gives a **shell export
precedence over `.env`**, so a generic `POSTGRES_PASSWORD` already
exported for something else would initialise this database with one
password while `DATABASE_URL` in `.env` still carried another — and the
failure would arrive as a connection error with nothing pointing at the
cause. Nothing else exports this name.
