# 883 — Tests that ran the real clock failed in the daily refresh's hour: decisions

Bug #883. Spec: `specs/080-daily-refresh-of-every-competition.md`, whose run refreshes every competition first when it starts at 03 UTC (`decisions/080-daily-refresh-of-every-competition.md`). Two unit tests ran the log on the real clock and expected no daily refresh, so between 03:00 and 04:00 UTC they failed on every branch, `main` included. Both are older than spec 080, which is what made them depend on the hour.

| Decision | Why |
|---|---|
| **A test that runs the log on the system clock pins it to 12:00 UTC** | The hour decides what the run does, so a test of the run states the hour. `prediction-log-service.test.ts` pins `Date` with Vitest's fake clock, which still ticks, and keeps testing the default clock path. `predictions-unreachable.test.ts` runs the script as its own process, so it preloads `tests/fixtures/clock-at-noon.mjs` through `NODE_OPTIONS`, which starts that process's clock at 12:00 UTC on a fixed day |
| **Not fixed by expecting whatever the hour gives** | A test whose expectation depends on when it runs checks a different thing at 03 than the rest of the day, and the daily hour's case is already tested with its own clock ("runs the daily refresh first in the run that starts at 03 UTC, with the run's own pacers") |
| **The unreachable-database run during the daily hour was measured, and is not a hang** | With its clock shifted to 03:00:05 UTC, `predictions log` against a listener that resets every connection exited 1 after 60.6 s with the same one line, `Predictions failed: read ECONNRESET`. At 12:00 it exits in 1.1 s. The minute is the daily refresh running first: every request waits its turn on the provider's pacer, football-data's nine a minute, before the database read fails. The test's 25-second timeout was too short for that, so it saw an empty stderr |
| **Production's 03:00 run with the database down is left as it is** | Read from the code, not measured, since the measured run had no provider keys: it does not hang either. Each competition's refresh fails at its first database read or write and is reported, the run's own database read then fails, and it exits as above, one line and exit 1. The provider requests made before those failures are spent. Reading the database first would change the order spec 080 chose, the refresh before the run's own reads, for an outage that the failed run already reports |
